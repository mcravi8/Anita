# Buddy for Mac · 0.23.1

Buddy is a personal Mac app with minimal direct messages, 3D avatars, and agents whose names, roles, instructions, shapes, and colors you can change independently.

Choose your first Buddy's name and look, then start chatting. The agent immediately asks about its job and desired result. Follow-up questions adapt to your answers, with no fixed count. A separate background Claude API call turns the answers into the agent's role and operating instructions; View instructions opens the editable agent settings. Setup choices and answers survive reopening, and failures retain them for retry. Fresh installs start without a fixed sample team. Existing workspaces retain their saved work during updates; removing all agents is a separate explicit local operation. Available service connections and shared-file access follow the requested default-on policy, with removals available per agent.

Open Buddy in Applications. Text conversations now use your existing ChatGPT sign-in through the official Codex app-server installed on this Mac. Replies stream into the chat, can be stopped, and can be retried after a failure. Each agent has its own direct-message history. Groups have a separate shared history and a real coordinator: it chooses a spokesperson, assigns up to three useful contributions, runs independent work together, passes completed work to dependent reviewers, and combines the results into one streamed reply. The main chat stays quiet; the small Teamwork link opens actual assignments, status, and contributions on request. Settings → Connections lists installed service connections available through your ChatGPT account. Every agent, including newly created agents, starts with access to every available connected service. Choose a service to remove access for individual agents. New connections become available automatically; explicit removals persist. Supported actions are enabled. Reading tools run normally; sending, deleting, publishing, and other changes request user review in the conversation through the connector’s approval flow. Updated instructions are explicitly applied before each reply. Chats, drafts, and agent settings survive app restarts.

## Connection

Choose ChatGPT or Claude in Settings → AI provider. ChatGPT and connected-service features require the Codex CLI and a ChatGPT sign-in on the same Mac. Claude conversations use a Claude Console API key stored in Keychain. Buddy discovers Codex in `/opt/homebrew/bin`, `/usr/local/bin`, or `~/.local/bin`. If needed, open Settings → AI provider → ChatGPT → Connect. Sign-in finishes in the browser; credentials remain managed by Codex. Buddy does not read, copy, display, or save the authentication token.

The ChatGPT connection accepts subscription authentication, removes API-key environment variables from its child process, selects an available default model, and uses the account's subscription limits. It never falls back to OpenAI API-key billing. The separate Claude connection uses Console API credits and its configured estimated spending limit. Connection details are available from the small caption under the composer or Settings.

This integration follows OpenAI's documented app-server path for personal/local apps. It is not a commercial or hosted deployment. See [Codex App Server](https://learn.chatgpt.com/docs/app-server) and [Authentication](https://learn.chatgpt.com/docs/auth).

## What works

- First-agent onboarding with saved drafts, optional appearance choices, real connection status, a checked save, and an adaptive job interview in the new chat.
- Real direct conversations, independent agent instructions and histories, streamed answers, Stop, Retry, and interrupted-reply recovery.
- Create a new agent, or copy an existing agent's shape and configuration without changing the original.
- Real group conversations with configurable membership and goal, role-based assignments, dependent handoffs, shared history, each assigned agent answering in its own message, and Stop/Retry. Group execution uses only connections enabled for every member; individual access removals apply to the whole group.
- Real connected-folder files: agents and you can read, create, and edit text/code up to 1 MB and DOCX/XLSX/PDF documents up to 32 MB in the shared folder and additional folders you connect. Chat cards come from successful native saves. Two agents cannot overwrite the same old version; the second rereads and merges. Previous contents are backed up, and Saved versions lets you restore them. File access defaults on and can be removed per agent. Groups require all members’ access.
- Real agent suggestions from direct and group conversations, with native pending records and human-only editable approval. Shared task boards remain frontend previews. Old sample direct messages collapse once a real conversation begins and are excluded from model history.
- Drafts survive switching chats and reopening Buddy. Multiple agents may answer separate direct messages concurrently.
- Native save/export dialogs and standard Mac menus: Command–N, Command–K, and Command–comma.

## Buddy 0.15 — recorded email reviews and routines

`buddy_review_inbox` runs a native read-only Gmail lookup: it verifies the account, paginates a targeted query (up to 20 × 100 IDs), deduplicates IDs, and reads full MIME bodies (up to 80 messages / 300 KB of evidence per turn, 20 KB per body). Page/read/body limits and unavailable messages are explicit gaps, never evidence of an empty inbox. All returned pages, full-read IDs, skipped IDs, and failed IDs are saved with the real query and timestamps under `InboxReviews`; raw bodies and credentials are not stored there. Gmail full-message snake_case and camelCase schemas are supported. Broad assessment lookups get a targeted 90-day preflight including archived/spam mail, invitations and follow-ups. Explicit date/count constraints are left for the requested scope rather than silently expanded. Exhausting keyword search pages does not establish completeness of a mailbox. Findings must cite sources and distinguish inferred deadlines/completion from verified facts; unsupported historical explanations or message ranks are forbidden. Older chats have no retroactively invented receipts. Search details appear in a collapsed disclosure under replies and background results.

Email routines use a separate, account/workspace/agent/routine/query/goal-scoped ID ledger. Before finishing, the agent records one analysis finding per fully read source with `buddy_record_inbox_review`; missing/duplicate/foreign IDs fail validation. Reading a source alone cannot advance routine memory. Only a successful run commits non-uncertain findings. Failed, truncated, unclassified and uncertain messages remain eligible for retry. The next occurrence searches for relevant new messages, skips successful prior reviews and carries the previous result forward for unresolved items. A separate structured ledger retains up to 200 unresolved source-linked findings so summary truncation cannot silently drop older pending work. A newer fully read message can reconcile an old finding through a validated update referencing both IDs; exceeding the limit blocks memory advancement explicitly. A new message in an existing thread has its own ID and is reviewed. Broader context can still be fetched when required; changed criteria or Gmail accounts do not inherit stale skips. This avoids repeatedly downloading unchanged mail; it is not a guarantee that model classification can never miss something.

An explicit “run this every morning” can invoke `buddy_manage_routine`, returning an actually saved routine ID, timezone, days, time and next run. Unspecified morning defaults to 09:00 in this Mac's timezone. A recognized recurring request cannot finish as successful without an active native routine receipt. Hypothetical examples do not create schedules. Background work → Routines supports creating, inspecting, editing, pausing, resuming and removing schedules directly. Provider and per-run estimated Claude limit are pinned when the routine is created; disabled providers/permissions block execution, with no fallback. Email routines require a targeted Gmail query and ChatGPT/Gmail connected, including when Claude analyzes them.

The existing single background helper ticks local saved schedules when logged in. This Mac must be awake and online. ## The task database

Background tasks and saved routines used to live in two JSON files that were rewritten in full on every change. They now live in one SQLite database, `Worker/operations.sqlite` (the system SQLite, no added dependency; owner-only; write-ahead journal with `synchronous=FULL`). A change is one transaction on one row, so ending the worker at any moment leaves each change whole or not made at all, and a progress update no longer rewrites the entire history. Each task row keeps the task's dictionary as JSON next to a few indexed columns (workspace, agent, request ID, status, version, archived), so the code above the store sees what it always saw. The database itself refuses a second live task for one request ID. The archive is a flag on the row rather than a separate file.

**First start after updating.** The worker checks `tasks.json`, `tasks-archive-*.json` and `routines.json` exactly as before, copies them into `Worker/Backups/pre-database-<id>.zip` (checked with `unzip -t` and a listing), imports them in one transaction, counts what it wrote before committing, and then renames the old files to `*.migrated`. Nothing is deleted, task and routine IDs and next-run times are unchanged, and a file that does not verify stops the start with every old file untouched. If the worker is ended after the commit and before the renames, the next start finishes the renames and does not import again. A file with an old name but different contents that appears later is left alone and never imported.

**Rolling back.** The `*.migrated` files and the ZIP are the recovery copy as of the update. Do not restore them over a database that has run since: it holds newer tasks and approval receipts. An older Buddy build started after the update sees no `tasks.json` and starts with an empty list.

**Who reads it.** The worker is the only writer. The inbox "prepared result" reuse and the team monitor read it through `BuddyOperationsDB.snapshot`, which falls back to the old files only while no migrated database exists. `install.py` reads the queue from the database before refusing an update while work is running, and `reset_agents.py` removes the workspace's rows and keeps them in its recovery archive (`Worker/operations-export.json`).

**Also fixed here.** A task stopped mid-attempt stored its allowance as a whole-number `0`, which `as? Double` cannot read, so until the worker restarted it looked as if it still had its whole budget: it could be resumed with no new allowance, and an allowance chosen for it was refused. Money amounts are now stored as decimals on the way in.

Tests: `tests/OperationsDB.swift` imports a full old history (live and archived tasks, two archive files with deliberate duplicates, routines, a paused queue), checks the ZIP byte for byte, refuses seven kinds of damaged input without touching the files, and ends the process (`_exit` in a child) just before and just after each of ten commits and at both ends of the import, checking each reopened state against a reference run and the database integrity check. `test_saved_queue.py` and the extended `test_reset_agents.py` cover the two scripts.

### Attempts, history and the outbox

The database is at schema version 2. A database left at version 1 by the previous update is brought up on the next start; one written by a newer Buddy is refused.

- **Attempts** (`attempts`): one row each time a task starts a try (`attempt` goes up): the number, the run ID, the provider and model, when it began, and how it ended (`completed`, `failed`, `interrupted`, `paused`, `cancelled` or `waiting_user`; `waiting_review` does not end it). A row with no outcome is a try still going. Attempts begin with this version; earlier ones were never recorded, so none are invented.
- **History** (`events`): every task keeps an ordered list of what happened to it. `id` orders every event of every task; `seq` numbers one task's events 1, 2, 3 with no gap. Types: `task.created`, `task.status` (`from`, `to`), `attempt.started`, `attempt.ended`, `task.archived`, and `task.imported` for the one starting entry of a task that was already there when history began. Each has a `cause` (`request`, `resume`, `worker.restart`, `history.limit`, `history.begins`, or empty when the caller did not say) and a `correlation` (the request ID the task came from). Progress text and the growing result are not events. Read it with `history(of:after:)` and `attempts(of:)` on `BuddyWorkerStore`.
- **Same transaction.** An event is written in the same transaction as the change it describes, so a task's status and its history cannot disagree, whenever the process ends. Asking again for a request that already has a task adds no task and no event.
- **Outbox** (`consumers`, `outbox`): `register(consumer:)` signs something up for events; from then on every new event gets a row for it, written with the event (`replayHistory: true` also queues what already exists). `undelivered(for:)` lists what it has not handled, oldest first. `deliver(_:to:effect:)` marks an event handled and runs `effect` in the same transaction, so an effect on this database and the record that it happened stand or fall together; if the effect throws the event stays waiting. Handling the same event again does nothing and returns false. An effect outside the database (a message, a notification) can still run twice after a crash between the effect and the mark, so it must use the event's `id` as its key.
- **Trimming.** Past 100,000 events, the oldest events of archived tasks are dropped, never one a consumer still has to receive.

Nothing reads this yet: no consumer is registered, so no outbox rows are written and the UI behaves as before. It is the base for the next slices (leases and action records, the budget ledger, and the single record of what needs the user).

Tests (`tests/OperationsDB.swift`) add: a scripted task life checked entry by entry; the process ended just before and just after each of eleven commits, with history checked against state both on the raw tables straight after the end and again after the restart tidies up; a restart that finds running work; the upgrade from version 1; delivery with a failing effect, replay of every event, and the process ended before, during and after the commit that marks an event handled; and trimming that leaves unhandled events alone.

### Actions: sent, unconfirmed, and checked off

The database is now at schema version 3 (a version 2 database is brought up on the next start). Every action that needs the user's approval (a browser operation, a sign-in or email-code step, a command with network access, a connected-service request) has one row in `actions`, written in the same transaction as the task's `reviews` entry it belongs to, so the two cannot disagree.

- **States.** `proposed` (shown for approval), `approved`, `dispatched` (handed over to be performed), then `confirmed` or `uncertain`; and `declined`, `expired`, `not_sent` and `failed` as the other ends. The record only moves forward, so a late copy of a review from the connection service cannot move an action backwards, and a finished action stays as it finished. An `uncertain` action can later be settled as `confirmed`, `not_sent` or `failed`. Each change is an event (`action.proposed`, `action.dispatched`, `action.confirmed`, and so on) with the action's ID, kind and tool.
- **"Dispatched" is saved first.** `markDispatched` is the last step before anything leaves the Mac. It is saved before the browser, the sign-in step, the command or the connection service is called, so a crash from there on means "may have been sent", never "approved only". It refuses, and the action is marked `not_sent`, when the attempt that proposed the action has been replaced (the record keeps the run ID that proposed it), when the task is no longer working, or when an identical action (same kind and same preview, fingerprinted with SHA-256) is still dispatched or unconfirmed in the same task.
- **A late receipt is still a fact.** A receipt from an attempt that was replaced in the meantime is recorded, and the action and its event are marked `late`.
- **Restart and stop.** Both settle every waiting action by how far it got: never approved becomes `expired` (restart) or `declined` (stop); approved but not yet dispatched becomes `not_sent` for the three kinds this app performs itself (browser, sign-in, command), and `uncertain` for a connected-service request, whose sending is done by the connection service; dispatched becomes `uncertain`. Before, any approved action became uncertain, even a browser operation that was never sent. Reviews of an unknown kind, and reviews saved before records existed (which are backfilled as dispatched), are treated as possibly sent. The task's progress text names the action: "The worker restarted while “Submit application” may have been sent. Check whether it went through before continuing."
- **Checking it off.** The task view shows each uncertain action under "Check whether this went through", with the exact operation, and two buttons: it went through, or it did not. That calls the worker's `resolve` operation (the user only; the model has no way to resolve an action). The Notifications list shows a task with an unconfirmed action as something to check, whatever state the task is in. Until the user answers, an identical action is held back, and the model's prompt for the next attempt lists what was done, what is unconfirmed (do not repeat; tell the user), what was approved but not sent (safe to propose again) and what the user declined.
- **Leases.** `acquireLease` gives one holder at a time exclusive use of a resource, with a generation number that only goes up. The same holder renews. A free lease, an expired one, or one whose holder `isLive` says is gone is taken over with the next generation. Releasing frees the resource but keeps the number, so an old token can never match a later lease, and `leaseIsCurrent` is the check to make just before something that must not happen twice. A worker that has just started frees whatever the last one held. The worker holds `browser:<profile owner>` while an attempt uses the private browser, and checks that it is still the holder before sending an approved browser operation.

Not done here (later slices): the connected-actions journal for chat conversations keeps its own states, and the single record of "what needs the user" that unifies these items with approvals and notifications.

Tests (`tests/ActionRecords.swift`): a full lifecycle with events; each refusal; late receipts and stale copies; restart and stop for every kind; the check-off; leases; the process ended before and after each of eleven commits of an action's life, with records, reviews and events compared both straight after the end and after the restart settles things; plus UI tests for the card and the notification.

## Quieter team oversight

A real journal showed the cost. In one day the monitor ran 46 check-ins, every one on a changed fingerprint, and spent $1.48 on them, while a whole scheduled email run costs 0.4 to 1.6 cents. Chief's own check-ins ran on Opus and 13 of 15 said nothing; each time Inbox's check-in said "notify", an Opus team summary restated the same finding in Chief's chat. Four changes:

- **Bookkeeping no longer counts as news.** An agent's fingerprint (what decides whether to run a check-in) is now built from what oversight watches for: a task ending or needing the user, a routine's status or error, a new message, a group entry ending. It no longer includes a routine's next-run time, timestamps, progress text of work that is not blocked, or a run being queued or started. A completed routine run that only repeats the run before it (see below) is left out too. An agent whose only work is in progress, with nothing else, has nothing to check and is not checked. Work that needs the user is still checked within a minute.
- **A report that only repeats is not sent up.** A check-in's report is compared with the last report that agent's check-ins sent up, and a team summary with Chief's last chat message. It counts as a repeat when it has no number (date, time, amount) the earlier text lacks, none of a short list of change words ("not", "cancelled", "moved", "failed", "replied", "received", "done" and similar) that the earlier text lacks, and at least 65% of the same words once filler is dropped. A repeat is recorded (`suppressed: "repeat"` on the check-in) but sends no team summary and posts nothing. The window is 24 hours, or 3 hours for a blocker, after which it is reminded. A check the user asks for ("Check now", or an agent's `check_in`) is never suppressed. On the real journal this rule separates cleanly: the repeats scored 0.75 to 1.0 with no new numbers, and the genuinely different updates scored under 0.25.
- **A routine run that restates the one before it** (at least 30% of the same words, no new number, no change word) does not count as a change. This is deliberately cautious: routine results are long and reworded each time, so on the real data 2 of 5 runs qualified.
- **Check-ins run on a small model.** On Claude, check-ins and team summaries use `claude-haiku-5-5` whatever model the agent chats with; ChatGPT agents keep theirs. The model can be changed with `configure` and `checkInModel` (empty restores the default); it is shown in the team status as `checkInModel`. There is no screen for it yet. Preference learning keeps its own model.

Limits. The repeat test is a heuristic about words and numbers, not an understanding of meaning, and it errs towards sending an update. Each agent's fingerprint scheme changed, so each gets one extra check-in after updating. The Gmail scan remembers the messages it has reviewed, but a message whose finding the model marks "uncertain" is deliberately not marked as reviewed (`reviewedIDs` in `BuddyInboxReview.swift`), so it is read and analysed again on every run, for ever. The real cursor held one such message, read in each of the last eight runs. That leak is separate from this change and is not fixed here.

Tests (`tests/TeamMonitor.swift`): restatement and window rules; fingerprint stability under each kind of bookkeeping change and its change under each real one; a second blocker with the same report, the same report reworded, a report with something new, a summary that repeats Chief's last message, and a requested check; the model default, the setting and its validation; and in-progress work not being checked. Each rule was broken on purpose and the tests failed.

## Emails read once, and nothing refused for being large

**Uncertain emails are no longer read for ever.** A message the analysis marks "uncertain" is deliberately not marked as reviewed, so that a later look can improve on it. Nothing ever stopped that looking: on a real mailbox one such message was read, put in the model's prompt and analysed again in each of the last eight runs. The cursor file now keeps a count in `attempts` (older files without it load as before; a damaged one is refused, not guessed). A message left uncertain is read at most three times (`BuddyInboxReview.uncertainReadLimit`). After that it counts as seen, so it is no longer read, but its finding stays open in the routine's memory and every run is still shown it (`previousFindings`), so nothing is dropped. A message that becomes a real finding clears its count, and a finding closed by newer evidence (an update with status `resolved`) now also marks its source message as done, where before it stayed pending. A message whose analysis was never recorded is still retried until it is, and is not counted.

**A long email is read, not refused.** An email over the text limit used to be recorded as a failed read ("needs a full follow-up read") that no later run could ever complete, so it was fetched and sent to the model again on every run. The limit is now 60,000 characters (it was 20,000), and a longer email is read and analysed from its first 60,000, flagged `truncated` on the message and listed in the coverage as `longMessages`, so the analysis can say so. It is done like any other once analysed. The per-run evidence budget (300 KB) is unchanged: past it, messages wait for the next run.

**An agent's status result trims itself to fit.** Chief reported that an agent status report was "too large for me to open". On the real data the team-status result was 91.6 KB, of which 83.9 KB was the text of the last 80 past check-ins, and it grew with every check-in. An agent's result now carries the last 20 check-ins with what happened and a 200-character summary of each report, not their full text (15.9 KB on the same data), and `BuddyTeamMonitor.fitting` caps any such result at 60,000 bytes by trimming a step at a time and only as far as needed: long text, then the sources per agent, then check-ins, then agents, and last everything but the core. It lists what it trimmed under `trimmed`, so the model knows it is a summary. The team screen is unaffected and still gets the whole history.

Limits that are still hard refusals, and not changed here: a worker response over 8 MB, a connected-service action whose details exceed 200 KB, a browser field over 12,000 characters, an Office package over 80 MB or a single part over 8 MB, files over 32 MB, and saved settings files over a few MB.

Tests: `tests/IncrementalInbox.swift` (the bounded reads, kept findings, unrecorded analysis, cleared counts, closed findings, old and damaged memory, long emails) and `tests/TeamMonitor.swift` (trimming at each step, small results untouched, past reports kept short, the screen still getting everything). Each rule was broken on purpose and the tests failed.

### The money record and daily limits

The database is at schema version 4 (a version 3 database is brought up on the next start). Every change to what a task may spend, has set aside, has spent or cannot account for is one entry in `budget_entries`, written in the same transaction as the task, so the ledger and the task cannot disagree: `authorize` (a task's allowance, or an extra one chosen later; asking twice adds nothing), `reserve` (set aside when an attempt starts), `spend` (what it really cost), `release` (the unspent rest, given back) and `uncertain` (a reservation abandoned with no cost reported). Money spent before the record began is entered once, on the day it was last changed, and is never counted as today's.

- **Limits.** A daily limit can be set for one agent or for the whole workspace (`limits`; an agent's own limit wins, otherwise the workspace's). "Today" is the local calendar day. What counts against it is everything an agent can spend: background tasks and routines (spent, uncertain, and what running tasks have set aside), and chat turns. A limit of $0 stops all paid work; removing it removes the cap.
- **Before paid work starts.** A background task that would pass the limit is not started: it is paused with a plain reason ("Today's limit for this agent ($10.00) would be passed: $8.20 is already spent or set aside, and this task needs up to $2.00. Raise the limit or wait until tomorrow, then resume."), nothing is set aside, the refusal is in its history (`budget.refused`), and it resumes when the limit is raised. A chat turn is capped to what is left of the day and refused only when nothing is left.
- **Chat spending** is recorded by the app in `Claude/spend-YYYY-MM.jsonl` (one line when a turn starts, with the most it may spend, and one when it ends, with what it cost). A turn that never reported is counted at its reserved amount as uncertain after two hours, so a crash cannot make money disappear. Only the worker writes the ledger and the limits; the app only reads them.
- **Seeing and setting it.** The worker's `status` carries `budget` (each agent's spent, uncertain and reserved amounts, its limit and the room left). A person sets a limit with the worker's `limit` operation. A model asks through a tool that checks what the person said (added with Chief's settings).

Not here: the team check-ins keep their own daily limit; money shared between a parent task and its children arrives with delegation.

Tests (`tests/Budget.swift`): each money event as an entry; earlier spending kept on its own day; limits with fallback, rollover and validation; chat turns, including unreported ones; a task that would pass its limit; and the process ended before and after each of six commits of a task's money life. Seven deliberate breakages were each caught.

### One record per blocker, dismiss, and a "Working" list

The database is at schema version 5. What needs the person is now one record per cause in `decisions`, derived from each task's state and written in the same transaction as the task, so a blocker cannot be shown without its cause or outlive it. A decision's id is its identity: one sign-in request is `review:<review id>`, however many places show it; a task waiting for you is `waiting:<task>:<attempt>`; a failed or interrupted task `stopped:<task>:<attempt>:<status>`; an action that may have been sent `action:<review id>:unconfirmed`; a task stopped by a daily limit `limit:<task>:<when>`. A Claude task with no allowance left has an `allowance` decision, and that takes the place of a plain "stopped" (choosing the allowance is what ends it). Starting again in a new attempt is a new blocker; touching a task while it waits adds nothing. Opening and ending a decision are task events (`decision.opened`, `decision.resolved`), so a consumer can follow them. At start, tasks that were already waiting get their entry and entries whose cause has ended are closed.

- **Read and dismissed** are kept by the app (`notification_state`, by alert id), separate from each other and from the work. Marking read or dismissing an alert never approves, declines or resumes anything, and a dismissed alert that still needs you is still in its task. Marks for alerts older than 90 days are forgotten. The page keeps a copy (`activitySeen`, `activityDismissed`) for when the app has not answered, and the app's copy wins when it has.
- **The Notifications panel** has three tabs. *Needs you* lists the app's blockers (before the app reports any, task states stand in, as before). *Working* lists running and queued tasks with their progress; they are never unread and never counted. *Finished* lists completed work. Each alert can be marked read or dismissed, and a tab can be dismissed in one go. The bell, the chat badges and the Background work badge are computed from the same list, so they agree, and resolving a blocker removes every representation of it.
- The worker's `status` carries `decisions` and `notifications`; the `notify` operation sets read or dismissed by id.

Tests: `tests/Decisions.swift` (each kind, no duplicates, identity across attempts, events, read and dismissed state, blockers found at start, and the process ended at every commit; seven breakages caught) and `buddy-activity.test.js` (blockers replacing task states, working, native versus page state, agreeing counters; five breakages caught).

### Settings and standing rules, on the person's word

The database is at schema version 7 (version 7 repairs a version 6 database that an in-progress build had already made with the settings table in its earlier layout: rows are kept and gain who carries them). What the person asks for in chat is carried out, kept, and can be undone; and the person's own rules about an agent's work ("for the first three applications show me the CV; once I approve those, apply on your own") are kept natively and followed, not left to the model's memory.

- **The tools.** `buddy_agent_settings` (current, change, undo, list) and `buddy_agent_rules` (add, list, pause, resume, remove, reset) are in every direct chat. The model names the change and **quotes the exact sentence from the person's current message that asks for it**; the app (never the model) supplies who is acting and what the person wrote, and refuses the call unless the quote really is in that message (capitals, spacing and quotation-mark style are ignored; fewer than 8 characters never counts). A web page, an email, a file or another agent can therefore never change a setting or a rule.
- **Who may change what.** The person on screen always. An agent may change its own settings and rules; its manager (`managedBy`) and the team's supervisor (Chief) may change any agent's; only the supervisor may change workspace-wide settings. A staged-rule request that the model answers without saving a rule fails the turn with a plain message (`requiresRule`, the same guard as schedules), so a rule is never silently "understood".
- **What can change.** Per agent: name (unique, 40 characters), role (55), instructions (1,500), figure, colour, hidden, model, daily spending limit, proactive updates, and the three tools. Per workspace (supervisor): the daily limit, team check-ins on/off, their interval (5, 15, 30, 60 minutes), their model and their own daily limit. Every value is checked and a refusal says what is allowed.
- **Increases wait for one tap.** Turning a tool on, raising or removing a spending limit, switching check-ins on or making them more frequent is recorded as `pending` and shown as a card in Notifications (Allow / Not now); nothing changes meanwhile, and the model is told not to say it is done. Everything else, including every decrease, applies at once. The person's own changes on screen always apply.
- **A journal with an undo.** `setting_changes` keeps old and new value, who, how, the person's words and the outcome (`applying`, `applied`, `pending`, `declined`, `failed`, `undone`). Undo is itself a change that restores the old value, only the newest change to a setting can be undone, and an undo that would give access back obeys the same rule as any increase. A change to a setting the app itself holds is written after its entry says `applying` and confirmed after, so a stop half way is sorted out on the next start (`reconcile`: it counts only if the setting now holds the new value).
- **Who carries a change home.** Name, figure, colour, hidden and tools are kept by the page (`adopter = page`); role and instructions by the agent's saved profile in the app (`adopter = app`, through the same `edit` that the settings form and the setup interview use); the rest are written directly. Until an adopter has saved the change and acknowledged it, `BuddyAgentMemory.overlay` lays it over the workspace for everything that reads it, so a rename or a new instruction is in force at once, and beats learned preferences. The page adopts on an event and every few seconds (`buddy-agent-changes.js`): it applies the changes, saves, and only then acknowledges, so being stopped between the two just repeats harmless steps.
- **Rules.** A rule has the person's words, `then` (`proceed`: stop asking once the checks are done, or `ask`: show the work every time), `reviewFirst` (1 to 20), what it covers (browser steps) and optionally which kinds of work. An agent shows its work with `buddy_review_checkpoint`: a card with what is being shown, which check it is of how many, a note on what approval means, and a box for what to change. Only the person's "Looks good" counts, once per check, in `rule_approvals`; the check that reaches the number records the freedom and the announcement together. `Needs changes` sends the written feedback to the agent and counts nothing.
- **What an earned rule allows, and what it never does.** With the rule on and either earned or already checked by the person in this very task, an agent's browser step goes ahead without its own review, and is recorded with the rule that allowed it. The browser itself has already refused sign-in, passwords, one-time codes, payments, accepting terms and new accounts before a step reaches review, and connected-service actions (emails, messages) always ask. Pausing, removing or restarting a rule takes effect at the next step. A rule that only asks (`then: ask`) never lets anything through.
- **Seeing and controlling it.** *Rules & changes* in an agent's settings lists its rules (pause, turn back on, ask me again, remove) and recent changes from chat (undo, allow). A change waiting for the person is a card under *Needs you*; an earned rule is a notice under *Finished*. The worker's `settings` and `rules` operations carry these (with no actor, the person on screen).

Tests: `tests/SettingsRules.swift` (quotes, authority, validation of every field, the journal, the overlay, what waits and what does not, undo, interrupted changes, rules and their conditions; eighteen breakages caught), `tests/WorkerIntegration.swift` (settings and rules over the real worker connection, and a standing rule from first check to earned freedom to paused, through the real host with a scripted agent and browser), `tests/Providers.swift` (a stated rule that was not saved fails the turn, and the wording that counts as one), `buddy-agent-changes.test.js` and `rules-ui.test.mjs` (carrying changes home in order, the settings section, the cards).

### Skipping setup questions, and how a chat opens

An agent made from a team plan can arrive with a complete role and instructions and still be waiting for its setup interview, which blocks work in a team chat until it is answered. Now: where an agent with saved instructions (role up to 55 and instructions up to 1,500 characters) is waiting, the page offers **Skip the questions** in its chat, **Use these instructions and finish setup** in its settings, and, in a team chat, **Use their instructions** for every unfinished member at once (each is saved exactly as written, through the same `edit` as the settings form). The refusal itself now names who is not ready and what to do, and Chief is told to ask for interviews only when the person wants them or an agent has no real brief.

Opening a chat clears its unread signal (the alerts stay listed under Notifications, nothing is approved or dismissed), as does an alert that arrives while that chat is open and no panel covers it. A chat opens at its newest message, and again at the newest message when you return to it; while you are in it the page keeps following new messages only if you are near the bottom, as before.

A chat that opened at its first messages was the page redrawing the whole view (which rebuilds the message list at the top) several times right after opening. The redraw is now wrapped: the reader's place is noted and put back (at the newest message if the chat was just opened or the reader was near the bottom). The sidebar's rail is laid out on one grid with the wide sidebar, so going between them is a glide (`buddy-sidebar-motion.css`, `buddy-sidebar-motion.js`). Every agent keeps its row (Chief at y 130 in both; the rail used to push them 96 px lower), the agents' pictures and the footer icons sit on one vertical axis (x 39) and never move while the edge slides, the words are clipped by the edge and fade (early when narrowing, late when widening), and the four commands are placed from the sidebar's right edge so they ride it and settle into a 2 x 2 grid under the logo inside the header band. The toggle updates the sidebar in place instead of rebuilding it (a rebuilt element starts in its final state, so nothing would move). It takes 0.64 s with a gentle start and end (`--glide`, `--curve`); the earlier 0.3 s with a sharp start looked instant. On a narrow window the drawer slides the same way and stays visible until it has left. The page-wide reduced-motion rule turns all of it off.

Tests: `chat-open-setup-ui.test.mjs` (open at the bottom, redraws keep the place, signals cleared and kept per chat, the one-click offers in each place, over-long instructions not offered, six breakages caught) `sidebar-motion-ui.test.mjs` (gradual in both directions, drawer visible while leaving) and `sidebar-layout-ui.test.mjs` (rows, pictures and footer in the same place in both states, commands inside the header band, the sidebar kept rather than rebuilt, pictures still, commands travelling one way, words fading, five breakages caught) and the repair case in `tests/OperationsDB.swift`.

**A quote must ask for the change.** Having the exact words in the person's message is not enough: a reply made only of filler ("try again", "yes, go ahead", "do it") agrees to something or asks for a retry and never says what to change, so it cannot authorize a change or a rule. This came from Chief reading "try again" as leave to unhide three agents and give each a spending limit nobody had asked for. The model is also told to change only what was asked, and never to change a setting as its own way of fixing a problem.

**Hiding an agent changes nothing but where it is listed.** "Hidden" is only the page's grouping of the chat list; no part of the app that runs tasks, schedules, team check-ins, team chats or settings looks at it (setup that is still waiting is what keeps an agent out of team status, background work and team chats). The worker journey, team chat and settings tests now run with every agent hidden.

### Group chats: each agent speaks for itself

A group request used to end with one combined reply from a spokesperson, shown under the group's picture ("Your team"). Now the planning step chooses only the agents who need to speak (up to three), and each of them writes its own reply to the person in its own voice (`BuddyTeamService`): it appears as that agent's message, with its name and picture and its full text, as soon as it finishes, in handoff order. Nothing is combined and nobody speaks for the group. If a request needs no one in particular, the chosen spokesperson simply answers (`team.direct`), and a one-agent group is unchanged. If every assigned agent fails the request fails with each reason visible; if some finish, theirs stand and the rest stay visible and retryable.

The run keeps what each agent said, in order and under its name, in its `text` (the hidden reply message's body), because history, search and the chat's preview read the stored messages. `BuddyChat.presentation` hides that reply when agents answered for themselves, except where something still belongs to it (saved files, action cards, routines) or a partial failure needs its Retry. Tests: `tests/Teamwork.swift` (nothing combined, the run keeps each agent's words, one agent failing while another finishes, a request nobody else needed), `buddy-chat.test.js` and `team-activity-ui.test.mjs`.

### The app icon

The icon is the current logo (the dot-matrix head drawn by the figure engine) on a white tile. `icon-logo.png` is that artwork, saved by `make-icon-logo.mjs` (run it only when the logo changes; it needs Chrome and the worker's Playwright, which the build does not), and `render-icon.swift` puts it on the tile and writes every size the build packs into `Buddy.icns`.

**No "Name:" on an agent's message.** The coloured name above each message already says who is speaking, so the contributor is told not to begin with its own name, and a leading "Name:", "**Name:**" or "**Name: Title**" is taken off if one appears anyway (a heading keeps its bold). The run keeps what was said as "Name: text" for history and the sidebar preview.

**Agents in a group can run code and use websites.** An agent asked in a group to re-run a pipeline said it had no tool to run anything: group chats only gave it the team-status tool. They now get every tool a direct chat has (`BuddyWorkerClient.groupTools`): coding sessions, website tasks, longer tasks, settings, standing rules and schedules, so asking for something in the group is never answered with "do that in my own chat". The same checks apply as anywhere: a change needs the person's own quoted words from that message, and the settings engine decides who may change what. A task started from a group reports to that agent's direct chat and Background work, and the agent says so in its message; the daily spending limits and reviews apply as always.

**Coding sessions move files to and from connected folders natively.** A coding session's commands can only see its own project, and the only way to move a file there was to read it through the conversation and write it back out. That works for a short script and not for a dataset: a team's pipeline re-run stopped because copying one 529 KB data file that way would have cost more than the whole $0.50 task. Two native tools (coding sessions only) now do the moving in Buddy's own code, so the contents never enter the conversation:

- `buddy_copy_into_project` copies up to 200 files and 64 MB per call (32 MB per file) from a connected folder into the project. A path ending in `/` brings every file under that folder (`/` the whole folder), leaving out hidden files, links and dependency folders. The originals are only read, and copying again replaces the earlier copy.
- `buddy_copy_out_of_project` saves results back into a connected folder, under a new subfolder the agent names. It only creates files and never overwrites one of the person's, so a second run needs a new subfolder.

Each copy keeps the version check and history. A file that can't be copied (hidden, a link, missing, over 32 MB, already there when saving) is reported and the rest still copy, a folder bigger than one call says so, and a link a command left inside the project is never followed out of it. The coding instructions tell the agent to use these instead of reading and rewriting files.

**The team status no longer says the supervisor is "not chosen".** `supervisorChosen` only records whether the person has ever opened the supervisor menu; Chief is the supervisor either way, and runs the check-ins. Agents read this status, and Chief took the flag for an unfinished setup step and repeatedly told the person to pick a supervisor in a banner that does not exist. The status now gives `supervisorName` and no flag. The menu itself is Workspace settings → Teamwork & updates → Manage → Team supervisor.

**The team supervisor can be changed in plain words.** "Make Sage the team supervisor" was refused ("none of my tools can change that setting"). `teamSupervisor` is now a workspace setting (by name; only the current supervisor or the person on screen), shown by name in the settings, journalled and undoable like the others. Agents also no longer relay the "no tools" of their private status check-ins as a limit of their real work, and the routine tool says the finest schedule is hourly so an agent offers that instead of a once-a-day check.
